# E2E 测试结果

## 第二轮 E2E 测试（qwen3.7-plus-2026-05-26，改进脚本）

- **脚本**: `benchmark/e2e-test.ts`（改进版，带 token 预估 + 同项目迭代任务）
- **运行时间**: 6 分 30 秒
- **Token 预估**: 79,000（预算 500,000，占 15.8%）
- **结果文件**: `/tmp/dsh-e2e-ab/e2e-report.json`

### 任务设计

同一 Node.js 项目迭代，后续任务依赖前面的产出：

| Task | 内容 | 依赖 |
|---|---|---|
| task-1 | 创建项目骨架 (config.js + app.js) | 无 |
| task-2 | 基于 app.js 添加 router.js 路由模块 | task-1 |
| task-3 | 基于 app.js 添加 auth.js 认证中间件 | task-2 |
| task-4 | 修认证 bug：/ 不应要求 auth | task-3 |
| task-5 | 创建 test-app.js 测试所有模块 | task-1~4 |

### 结果

| Phase | 平均工具调用 | 平均评分 | 注入次数 |
|---|---|---|---|
| Baseline (无插件) | 1.2 | N/A | 0/5 |
| Enabled R1 (首次跑) | 6.2 | 0.910 | 5/5 |
| Enabled R2 (有经验) | 7.8 | 0.906 | 5/5 |

### 工具调用次数对比

| Task | Baseline | R1 | R2 | R2 vs R1 |
|---|---|---|---|---|
| task-1 | 1 | 3 | 4 | +33% |
| task-2 | 1 | 8 | 9 | +13% |
| task-3 | 1 | 5 | 10 | +100% |
| task-4 | 1 | 8 | 9 | +13% |
| task-5 | 2 | 7 | 7 | 0% |

**R2 vs R1: 工具调用 +25.8%，评分 -0.4%，经验注入未带来改善。**

### 分析

1. **Baseline 工具调用远少于 Enabled** — Baseline 无插件时，stderr 没有 self-improving 日志，工具调用数从 stdout 粗估（按代码块数），严重低估。实际工具调用不可比。
2. **R2 工具调用比 R1 更多** — 经验注入不仅没减少步数，反而可能因为注入的文本增加了 context 长度，导致模型更多次调用工具。
3. **评分基本持平** — R1 0.910 vs R2 0.906，差异在噪声范围内。
4. **5/5 注入成功** — 插件确实在每个任务都注入了经验，但注入的经验没有帮助 agent 更高效地完成任务。

### 根因分析

- **任务太简单** — qwen3.7-plus 能力足够，5 个任务都能直接完成，不需要历史经验指引
- **经验内容缺乏针对性** — 注入的是"上次用什么工具序列做了什么"，不是"这个 bug 该怎么修"的具体 lesson
- **context_hash 匹配不够** — 每个 task 的工具序列虽然部分重叠，但 taskPattern 不同（feature/bugfix/test-writing），P5 的同类优先逻辑未能匹配
- **单次实验噪声大** — LLM 输出有随机性，需要多次跑取平均

### 改进后的脚本（未跑成功）

重写了 `benchmark/e2e-test.ts`，改进点：

1. **Token 预估** — 跑前打印预算，超 50w 则终止。`--dry-run` 模式只预估不执行
2. **任务改为同一项目迭代** — 5 个任务有依赖关系（创建项目 → 加路由 → 加认证 → 修 bug → 加测试），后续任务工具序列与前面的重叠，经验注入才有可能帮上忙
3. **步数用工具调用次数统计** — 从 stderr 的 `[self-improving] tool/result` 解析，无插件时从 stdout 粗估
4. **加了文件数/代码行数** 作为辅助指标

## 脚本架构

```
benchmark/e2e-test.ts
├── Token 预估（--dry-run 模式只跑这一步）
├── Phase 1: Baseline（无 self-improving 插件）
│   └── 5 个连续任务，从空目录开始
├── Phase 2: Enabled R1（有插件，空 DB）
│   └── 同样 5 个任务，插件从零积累经验
├── Phase 3: Enabled R2（有插件，复用 R1 的 DB）
│   └── 同样 5 个任务，R1 的经验会注入
├── 对比报告
│   ├── 工具调用次数对比
│   ├── 评分对比
│   ├── 经验注入统计
│   └── 代码产出（文件数 + 行数）
└── 恢复原始配置
```

| Task | 内容 | 依赖 |

| task-3 | 基于路由添加认证中间件 | task-2 |

## 两轮 E2E 测试的教训

1. **任务必须连续有依赖** — 第一轮独立任务经验注入无效果；第二轮改为同项目迭代但仍未改善
2. **Baseline 工具计数不可比** — 无插件时 stderr 无 self-improving 日志，从 stdout 粗估严重低估
3. **Token 预估必须在跑前做** — dry-run 先行，确认不超额再正式跑
4. **单次实验噪声大** — 两轮都是单次跑，LLM 随机性导致结果不可靠，需要多次跑取平均
5. **经验注入不等于经验有效** — 两轮 R2 的注入率都是 5/5，但步数未减少。注入的内容（"上次用了什么工具"）对 agent 完成当前任务帮助有限
6. **任务难度不够** — qwen3.7-plus 能力足够直接完成这些简单编程任务，不需要历史经验指引。要体现记忆系统价值，需要设计"会犯错的困难任务"——如需要记住 API 版本差异、需要避免之前踩过的坑
